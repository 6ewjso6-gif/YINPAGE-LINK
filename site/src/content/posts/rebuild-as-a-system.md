很多重构看起来像换框架，实际上是在补同一个洞：网站长大了，但结构还停留在“页面集合”。

我读过一份很典型的复盘：四代仓库，SvelteKit、Vue、Astro、再回到 SvelteKit。表面上是技术栈轮换，真正变化的是，网站终于有了一套能自我解释的系统。

## 先问内容放在哪

第一代方案已经能直出 HTML，却把文章原文塞进列表页，搜索数据、RSS、SiteMap 各自读取一份。页面能开，系统却说不清“一篇文章”到底是什么。

后来做对的一件事很简单：把内容收进独立的内容层。页面只负责取数据，RSS、搜索索引、站点地图从同一个来源生成。

> 改一篇文章，所有产物都应该自动更新。做不到这一点，就还没有内容层。

## 再看设计系统

组件库不等于设计系统。Vuetify 有成熟组件，站点里却同时混着 Vuetify、Tailwind 和项目 SCSS；Astro 那一代有 6200 行全局 CSS 和一个 5400 行的组件。

第 20 次把全局 CSS 压到 150 行左右，不是因为样式变少了，而是因为复杂度从“两个巨型文件”重新分配到了组件树和 Token。

统一的关键不是把所有按钮涂成一个颜色，而是：删除永远是危险语义，空状态只有一种写法，移动端 Sheet 和桌面 Dialog 共享边界。

## 最后才是 HTML 与 JS 的边界

全站预渲染出 232 个 HTML，不等于关掉 JS 还能登录。它改变的是交付顺序：

1. 浏览器先拿到标题、正文、导航和基础状态；
2. JavaScript 只在搜索、筛选、登录、创作、弹窗时接管；
3. Markdown 解析、代码高亮、目录生成全部留在构建期。

这样做的直接结果是，功能变多了，客户端包袱却没有同步膨胀。

## 重构不等于搬家

还有一条容易被忽略的判断：不是所有旧功能都要继续占据主导航。保留业务结果，重排入口，旧链接用兼容页和归档接住，这比把每个旧按钮原样搬过来更合理。

框架会继续换。能留下来的，是内容层、设计语言和发布流程这三条边界。
